# Document Strict Work

Put each fact in its canonical source, make durable text describe the current target state, and review generated or composed output as readers receive it.

## Classify the artifact

Before editing, identify whether the requested artifact is:

- raw research or unedited source output;
- faithful extraction;
- synthesis or recommendation;
- current plan or implementation specification;
- durable repository guidance;
- product/API documentation;
- generated reference, snapshot, badge, or report;
- source fragment or template used to create another document.

Do not turn raw research into policy, synthesis into verbatim evidence, a plan into status history, or durable guidance into a work journal.

## Resolve the canonical source

- When the user refers to a goal, plan, or specification file without an exact path, resolve the authoritative artifact from explicit attachments, the active goal objective, and the most recent user designation before editing. Do not prefer a similarly named repository file or ledger merely because it exists. Ask only if those sources still leave more than one candidate.
- Put detailed API behavior in inline rustdoc when it is the canonical API source.
- Keep `AGENTS.md` and `CLAUDE.md` focused on durable facts that change agent behavior.
- Keep product-specific guidance in the product owner, not a reusable fragment package.
- Put reusable Markdown in its fragment owner and regenerate consumers.
- Edit templates, macros, generators, schemas, or snapshot workflows rather than generated output.
- Treat ignored and on-demand artifacts according to their repository contract; absence is not evidence they should be checked in.

When fragments compose into one document, review the final rendered order for duplication, contradiction, and template/product precedence. Do not treat each fragment as an independent essay.

## Write target-state-only guidance

Prefer present-tense, durable facts:

- actual ownership and command surfaces;
- stable invariants and non-obvious constraints;
- canonical sources and downward/upward pointers;
- behavior that future agents would otherwise misunderstand.

Remove:

- “earlier,” “previous,” “draft,” “superseded,” “landed so far,” and refactor narration;
- stale versions, statuses, future plans, or transient initiative notes;
- obvious hierarchy prose such as “this file adds guidance”;
- duplicated parent or child guidance;
- fake precision, exclusions, or policies not supported by source;
- private fixture identities, local aliases, or real user-specific values.

Do not repeat a slogan when the durable artifact needs enforceable constraints.

## Preserve scope and method

- In documentation-only work, edit only documentation in the authorized scope.
- Read each flagged file in full when required, plus only directly relevant neighbors.
- Do not fix adjacent code, lint, configuration, or newly discovered documentation warnings without authority.
- Use targeted edits; do not mass-reflow or rewrite unaffected prose.
- Follow local wrap conventions. Preserve semantic line structure inside code fences, tables, lists, and headings.
- If the user prescribes manual transformation, do not replace it with a script.
- If the user requires first-hand reading, the root must read; delegated digests are not equivalent.
- Preserve raw research files and provenance when requested.

## Route generated changes through the owner

A direct request to fix a named generated artifact authorizes the canonical local, non-network generation step needed to materialize that artifact when its expected write set is within the requested scope, unless the user reserves or forbids generation. It does not authorize publication, dependency rewiring, verification, staging, commits, or pushes.

1. Locate the source fragment, generator, macro, template, or snapshot command.
2. Change the source.
3. Run the canonical generation workflow only when authorized.
4. Review the complete generated output and every expected consumer.
5. Sweep stale paths through source, fixtures, help text, detection logic, and documentation.
6. Report generated fallout rather than hand-editing or weakening the workflow.

Missing tooling is a blocker or approval point, not permission to imitate generated bytes.

## Validate fidelity

Check that:

- every claim is sourced from current tracked material or an explicit user decision;
- ownership and scope match current repository guidance;
- public behavior is documented at its canonical surface;
- researchable facts are not presented as resolved without evidence;
- upstream implementation is not called a specification without an ADR, spec, or explicit compatibility requirement;
- raw evidence remains distinguishable from analysis;
- generated fragments compose cleanly;
- no stale path or obsolete vocabulary remains within the authorized scope.

Run only authorized documentation or generation checks. Do not use a broad audit as substitute verification when verification is prohibited.
