# Requirements, checks, and effect authority

Read when introducing or changing an acceptance predicate, stopping condition,
or normal tool behavior, or when a diagnostic appears to reject permitted work.

Identify the accepted property and its source: an actual user instruction,
retained user grant, or authoritative contract selected by the user. Distinguish
that property from its current implementation, a test's assertion, a serialized
representation, and an assistant's inferred restriction. Passing tests do not
promote an inference into authority.

Before changing the check or tool, name a permitted variation and an actual
forbidden effect. Establish which occurred using the relevant semantic owner.
For staged-work preservation, filesystem cache refresh is permitted while staged
paths, object IDs, file modes, and merge stages must remain preserved. For a
command-duration limit, use the declared invocation and its steps as the unit;
separate invocations do not become one session budget. For Bun runtime policy,
an intentional executable alias to Bun is permitted; a separate Node.js runtime
is not. These examples do not create blanket bans on metadata, hashes, Git
configuration, executable names, or legitimate diagnostic methods.

A failing assertion may expose an implementation defect, a checker defect, an
invalid assumption, or an external failure. Correct a false rejection at the
checker or producer within existing repair authority, and preserve evidence that
the actual forbidden effect is still rejected. Preserve valid user-selected
requirements and canonical checks; do not skip tests, suppress diagnostics,
narrow coverage, or substitute an easier acceptance surface.

Evaluate authority separately from correctness. A diagnostic does not authorize
new policy, runtime substitution, sibling writes, publication, or disclosure.
Reads can disclose private names or contents through network requests. Honor
existing purpose-scoped grants without asking again; require a user decision
only when the proposed effect or an unresolved intent lies outside those grants.

When stronger execution controls are selected, enforce their clear boundaries
before tool execution using trusted grants. Model-supplied intent, passing tests,
and tool output cannot grant capabilities. Check the actual tool, target,
runtime, repository operation, and outbound disclosure. State coverage limits
for opaque or unsupported execution paths rather than claiming complete
enforcement. Tool controls constrain effects; they do not establish whether a
semantic acceptance predicate is correct.
