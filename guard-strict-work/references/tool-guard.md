# Native pre-execution guard

Use the `Rust` package at `scripts/tool-guard/` when the user selects execution controls. Build its `strict-tool-guard` binary with `cargo build --release` and run it as a native `PreToolUse` command with `--policy <trusted-policy-file>`. The `--inspect` mode returns the complete typed decision for diagnostics. Ordinary mode returns a native denial for a refused effect and an empty response for an accepted inspection. Acceptance abstains: it cannot grant tool authority or override native approval and another handler's refusal.

The policy belongs to the operator. Model tool arguments cannot add grants. Bind a scoped policy to `session_id` when its authority is session-specific. Optional `repository_roots`, `write_roots`, `allowed_git_operations`, `github_owners`, and `network` constrain their named supported effects. A missing optional scope adds no new restriction. `destructive_git_grants` names exact selected operations; an ordinary commit/push grant does not permit reset or force push. `require_normal_git_refresh` is conditional on an accepted requirement, not a global ban on legitimate diagnostic settings.

The baseline policy preserves ordinary execution while refusing recognized separate `Node.js` runtime installation and destructive `Git` operations without their own grants. Resolve `node`, `npm`, and `npx` aliases against the actual `Bun` executable; do not classify documentation or quoted arguments as calls. Executable names ending in `.exe` use the same identity check. Shell wrappers such as `.cmd` files require their own interpreter inspection rather than a filename-only compatibility claim.

Register the native hook alongside existing handlers, obtain its normalized identity from `hooks/list`, and persist trust for that exact handler through the native configuration API. Do not bypass hook trust or enable unrelated handlers. Confirm trusted registration and prove refusal before an actual effect. File installation or hook discovery alone does not prove activation. Record the runtime and environment where the observed refusal occurred; do not imply coverage for another running harness without its own evidence.

The guard inspects literal invocations and supported tool payloads. A parsed command is not proof of every effect of its executable. Explicit write-tool destinations resolve existing symlinks and normalize missing path components before scope comparison. Git scope inspection uses the supplied working directory and literal `-C` arguments; named remote resolution preserves literal `-c` settings and Git's URL rewriting. It does not establish containment of arbitrary shell writes, changes of directory inside shell bodies, custom transport helpers, executable aliases, environment overrides, or redirects to additional remote endpoints.

Dynamic shell code, arbitrary interpreter bodies, shell functions, unknown tools, indirect network requests, and changes between inspection and execution require stronger native sandbox or capability boundaries for complete containment. Partial or unsupported syntax/tool decoding reports that coverage. `require_literal_shell` can refuse unsupported syntax when the selected workflow requires that restriction; do not silently impose it on every user task. A hook that cannot start, crashes, or times out may be handled by the native harness differently from a returned denial; a hook is not an operating-system sandbox.

Keep helper tests, native hook integration, and actual agent evaluations as distinct evidence. Evaluation fixtures use isolated workspaces, synthetic data, local fake endpoints, and real tool traces. Do not contact live home devices or private third-party services to exercise a refusal case. `$verify-strict-work` owns the authorized behavioral evaluator and its effect checks.
