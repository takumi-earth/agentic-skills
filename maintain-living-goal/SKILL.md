# Maintain Living Goal

Keep unfinished work and goal-owned authority sufficient to resume. Apply the already-loaded contract throughout the task; another slice or status question does not require rereading unchanged instructions.

## Resolve the designated authority

When the active harness supplies an exact goal path, that is the sole mutable goal authority. Read that path directly. Do not enumerate, compare, timestamp, size, or select sibling attachments using conversation, memory, or summary hints. Read another attachment only when explicitly designated as historical input. If two sources are explicitly active, ask which governs before editing either. Without a harness path, use the latest explicit user designation or current goal metadata; never choose a similarly named repository file by convenience.

Keep active authority, historical provenance, supporting evidence, and authorized output distinct. A link or role label does not establish authority or expand read/write scope. Reuse complete, unchanged material for ordinary status answers. Refresh relevant facts after a substantive change or attribution uncertainty; after actual context loss, use `$resume-strict-context` and its complete-read recovery.

## Honor the selected retention model

Use the user's current instructions for what the goal must retain. The default is the objective, unfinished implementation and decisions, and genuinely goal-owned protected requirements. A source-complete item leaves the unfinished list after its durable owner is current when that model permits removal.

- If the user requires a standalone goal, preserve its load-bearing architecture, rationale, order, barriers, counterfactuals, and evidence obligations there.
- If the user selects repository guidance or another exact document as the durable owner, update that owner and retain only the concise authoritative reference needed to resume. The referenced contract must be current, accessible within scope, and read when its detail is needed.
- Do not move a protected packet or change its owner merely to save tokens. A user's selected owner or explicit supersession must authorize that transition; a summary, partial implementation, or assistant-authored label cannot.
- Remove completed-work history, agent narration, diagnostic chronology, copied procedure, and verification-result history. Keep unresolved requirements and deliberately unrun obligations distinguishable; do not recreate source-complete work because acceptance remains pending.
- Verification or acceptance still required by the task remains required even when the selected implementation-goal model keeps it outside this file. Preserve the original objective and report the boundary in existing task context; do not invent another ledger.

Before an authorized goal edit, identify which affected requirements or facts changed. Do not reconcile an unchanged goal before every source edit. For substantive pruning, load [slices-and-pruning.md](references/slices-and-pruning.md); it preserves statement-level attribution and contradiction checks without restoring chronology.

## Preserve authority and phase

A goal edit records existing authority or evidence; it never creates permission, selects a new design, changes a baseline, retires a capability, or invents a replacement test. Separate user selection, application, and verification. A settled choice stays settled unless the user supersedes it; changed bytes or Git representation can stop application without reopening that choice.

Before a protected edit, provenance dispute, or correction with dependent claims, load [goal-provenance.md](references/goal-provenance.md). For the concrete baseline/retirement regression, load [autonomous-goal-edit-regression.md](references/autonomous-goal-edit-regression.md). Preserve complete protected packets and retract affected assistant-derived statements rather than laundering a proposal through mutable status.

Choose one complete implementation slice in the current user-selected phase. An independent lane requires a concrete unfinished user requirement and an already-authorized next effect in that phase. Pending implementation does not authorize standalone test migration, evidence collection, optional audits, or preparation for an unselected future decision.

## Report state without adding history

Answer from designated authority and relevant existing evidence. Keep planned, written, compiled, executed, assertion results, process exit, canonical acceptance, and user acceptance distinct. Source or exit `0` alone does not prove executed behavior. Changed inputs invalidate only affected current claims; a later verification ban does not erase earlier results that still apply. Classification authorizes no new read, gate, ledger, or goal rewrite.

When no authorized unfinished effect remains, report the boundary once and stop. A continuation or `Stop` retry cannot create work, strengthen an unchanged audit, or authorize another evidence artifact. For an actual whole-goal impasse or completion candidate, load [goal-state.md](references/goal-state.md) before proposing a status transition. Preserve the harness-owned genuine repeated-blocker threshold.

Only the user's explicit acceptance of the completion candidate or direct instruction for that transition authorizes `update_goal(status: "complete")`. Passing gates, elapsed effort, and an agent's favorable audit do not establish acceptance. Update memory only when explicitly requested.

## Conditional adapter work

For implementing, debugging, testing, configuring, or explaining the packaged goal resolver, completion-handoff adapter, or `Stop` adapter, load [hook-adapters.md](references/hook-adapters.md). Also load it when an actual adapter event requires its exact artifact-selection or handoff protocol. Ordinary implementation, status, and pruning do not need runtime-root parsing, hook envelopes, database queries, or adapter test procedure.

Artifact creation, hook registration, trust, and activation remain separate authorities. Automatic post-completion skill review belongs to `$auto-skill-enhancer`; moving this procedure does not alter either adapter's lifecycle behavior.
