# Strict-owner reference variant

## Concrete intent

Make role-correct real fixtures a shared invariant enforced by existing strict planning, implementation, causal, and verification owners rather than a parallel execution phase.

## Approach

Route fixture decisions through the current strict phase owner and provide one selectively loaded reference containing the planning and implementation handoff fields.

## Preserved nuance

This variant keeps authorization and phase ownership with existing skills. It still treats role identity as stronger than byte deduplication and refuses runtime substitutes for file-consuming workflow boundaries.

## Relationships and uncertainty

This is an alternative to the standalone fixture-contract variant. Review should decide whether distributed owner integration is reliably trigger-reachable or whether the user correction needs its own discoverable skill.

## Review questions

- Which existing strict owner should link the shared reference if this approach is selected?
- Would routing through several skills make the invariant easier to miss than a standalone trigger?
- Should the causal-edge wording live only in `$protect-causal-architecture`?
